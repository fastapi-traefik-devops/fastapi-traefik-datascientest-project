08CI/CD — the flow

GitHub Flow model — one main, always deployable; short-lived branches + PRs

GitOps — Jenkins never touches the app cluster; it commits which image runs where

Build once, deploy many — same image dev → stage → prod; only config differs

Phase 1 · doneCI → 18 gates → verified images → GHCR

Phase 2 · nextGit promotion → Argo CD → K2 / K3

Tatiana · 1:30. Three rows = three environments. Row 1: any branch can go to dev, manually, with approval. Row 2: every green merge to main goes to stage automatically. Row 3: a version tag reuses the exact stage images — no rebuild — and production changes only when a human merges the release PR. In every case Argo CD does the deployment, Jenkins only writes Git.

09CI/CD — Jenkins jobs, release & rollback

app-ci · CI agent

18 gates: secret scan → lint → unit / API / E2E → dependency audits → Docker build → non-root smoke → Trivy → attest. No credentials.

trusted/publish · publisher agent

Separate agent. Checks CI = SUCCESS, Git SHA, all gates and archive hashes → pushes sha- tags to GHCR. Refuses a changed tag.

Phase 2 · release v1.2.0

  1. Tagged commit must be on main
  2. sha-<commit> images exist in GHCR and match stage history
  3. Jenkins approval: "this ran healthy in stage"
  4. Retag existing image as v1.2.0 — no rebuild
  5. release/v1.2.0 → PR to prod overlay → merge = approval

Rollback = git revert

  • Every deployment is a commit → revert it, Argo CD syncs in minutes
  • No rebuild: old digests stay in GHCR
  • DB migrations aren't auto-reversible → check schema

Verifiedfull Phase 1 CI green (18 gates); earlier on minikube: CI → GHCR → Argo synced stage

Not yetPhase 1 run from main + GHCR push · promotion · prod

Tatiana · 1:30. Two jobs on two separate agents: the CI agent has no credentials; only the publisher can push, and only after it has checked the CI result, the commit, every gate and the archive hashes. Release and rollback are the Phase 2 design — the GitOps part was already proven on minikube. Be honest about what is verified.

11Security (DevSecOps)

Image scanning

Trivy on every image: HIGH / CRITICAL or a secret blocks the build. Jenkins images: 0 High / Critical.

Dependencies

pip-audit + npm audit as blocking gates, Dependabot for updates. npm: 62 → 0 vulnerabilities.

Secrets

Sealed Secrets in Git; Gitleaks scans code + full Git history; CI test secrets generated per run.

Secure pipeline

Only the publisher holds the GHCR token; CI agent has none. Builds in isolated Docker-in-Docker over TLS, no host socket.

Hardened runtime

Non-root images, digest-pinned bases, healthchecks; TLS on stage / prod ingress; Adminer not exposed.

RBAC (bonus)

Argo AppProject whitelist: no Secrets, Namespaces or cluster resources; pods without SA tokens.

Known limits: Docker-in-Docker stays privileged (isolated CI host, no credentials) · untrusted fork PRs would need throwaway workers · cert-manager for TLS is next

14Challenges & lessons learned

kube-vip.io blocked by our host

The install fetched the kube-vip RBAC manifest from kube-vip.io — blocked from our server. We vendored rbac.yaml into the scripts, then into Ansible.
Lesson: no external URLs at install time — pin and vendor.

30+ minute builds

BuildKit saturated the shared 8 cores; every k8s CI pod started with an empty cache. Now: permanent Docker agents with a persistent build cache.
Lesson: caching matters more than more clusters.

Jenkins disk full

Builds failed with ENOSPC on minikube → investigation report + runbook.
Lesson: a Running pod ≠ a healthy pipeline.

Security clean-up

npm 62 → 0 vulns; Jenkins agent 47 High + 1 Critical → 0 by rebuilding tools from pinned sources. Kaniko → BuildKit; k8s agents → Docker agents.
Lesson: scanners must block, not warn.
